# ФСП Job Board

Платформа подбора IT-специалистов с **обратной механикой**: кандидаты распределяются по категориям (специализация × грейд) по результатам адаптивного теста, а работодатель сам находит нужную категорию и выходит на конкретного человека с предложением и зарплатой. Профиль усиливают достижения в соревнованиях Федерации спортивного программирования (привязка ФСП ID).

## Ключевые механики

**Тестирование, устойчивое к утечкам.** Задание — шаблон-генератор: числа, данные и код меняются для каждого кандидата, правильный ответ вычисляется (код и SQL исполняются). 303 семейства заданий; код в заданиях — на языке заявленного стека (Python, JavaScript, TypeScript, Java, Go, C#, PHP; фреймворки React и Vue), ответы сверяются с настоящими компиляторами и интерпретаторами в CI; без повторов шаблонов между попытками кандидата; адаптивный тест (IRT 3PL + классификационный CAT) решает, выше ли способность кандидата порога заявленного грейда, в среднем за 16 заданий (29 за весь онбординг с попытками на ступень ниже или выше). Состав теста — ядро специализации (общее для всей категории) и модули по заявленному стеку: проверяется то, что кандидат заявил, чужой язык не подставляется. Грейд по результату не понижается; смена подтверждённого грейда — не чаще раза в 90 дней. Мониторинг утечек (CUSUM) и онлайн-перекалибровка параметров заданий (MML-EM).

**Практический кейс из области кандидата.** Для Middle+ после теста знаний — кейс с уточняющим вопросом. Сюжет подбирается по направлению (CV, NLP, рекомендации, временные ряды) и отрасли из опроса — например, «детектор фолов по видео» вместо «оттока клиентов банка», — а критерии оценки у всех версий кейса общие, поэтому сложность сопоставима.

**Цифровой проктор (по желанию).** Камера и микрофон анализируются в браузере (Human/TF.js): телефон в кадре, второе лицо, речь вслух, выключенный микрофон или камера. Видео не записывается; на сервер уходят счётчики событий и эмбеддинг лица для сверки 1:1 с эталоном профиля (в production — ЕБС). Работодатель видит отметку «Тест с проктором», а после принятого приглашения — кадр с теста, чтобы сверить лицо на собеседовании.

**Подбор и выход на контакт.** Работодатель описывает потребность текстом → NLP выделяет стек, специализацию и грейд → рекомендованные категории и ранжированная подборка с объяснением («подтверждено тестом», «заявлено», «чего не хватает», «вилка в ожиданиях») → уточнение фильтрами без потери подборки (уточнения можно сбросить) → приглашение с обязательной вилкой «от–до». Контакты кандидата открываются только после принятия приглашения или собственного отклика.

Ранжирование (формула v7): требования вакансии весят по их специфичности в категории, жёсткие расхождения (основной стек, формат, вилка) работают как «ворота», вес достижений ФСП — 14% итогового скора, и они засчитываются как опыт работы — платформа поднимает молодых участников соревнований без коммерческого стажа. Опционально — гибрид с локальным кросс-энкодером (`FSP_RANKER=hybrid`).

**Валидация** (`make validate`: синтетическая популяция со скрытой истиной и намеренно рассогласованной моделью ответов):

| | Наша механика | Поиск по ключевым словам (BM25) |
|---|---|---|
| Качество подборки NDCG@10 | **0.70** | 0.18 |
| Ожидаемые принятые приглашения в топ-10 | **3.9** | 1.0 |
| Ложные подтверждения грейда при утечке 50% банка | **23%** | фиксированный тест — 60% |

Точность грейда — 72.3% точно (среднее по 5 сидам, разброс 71.5–73.2%) и 99.9% в пределах ±1 ступени при завышении 4.2%; повторное прохождение — взвешенная κ 0.83; онбординг — в среднем 29 заданий.

**Бенчмарк подбора со слепой разметкой** (реалистичные свободные тексты резюме и вакансий, сгенерированные по скрытым профилям; nDCG@10 по слепой разметке LLM-асессора, не знающего, какая система нашла кандидата): формула v7 — **0.82**, v5 — 0.79, v5 + кросс-энкодер — 0.81, исходная формула v1 — 0.70, лучший нейросетевой бейзлайн — 0.65.

## Быстрый старт (Docker Compose)

Требования: Docker 24+ с Compose v2, ~4 ГБ свободной RAM, свободные порты 18000, 18025, 18080, 18088, 18090.

```bash
git clone https://github.com/Izymka/fsp-job-board.git && cd fsp-job-board
cp .env.example .env    # для локального запуска можно ничего не менять
make up                 # = docker compose up -d --build + HTTP для админки Keycloak; первая сборка ~3–5 мин
```

| Адрес | Что там |
|---|---|
| http://localhost:18088 | Платформа |
| http://localhost:18088/api/docs | Swagger UI (OpenAPI) |
| http://localhost:18080 | Keycloak (админ — из `.env`, по умолчанию `admin` / `admin`) |
| http://localhost:18025 | Mailpit — письма подтверждения email и уведомления |
| http://localhost:18090/docs | Реестр ФСП (имитация) |

При старте бэкенд применяет миграции и загружает демо-данные: ~300 кандидатов, прошедших симулированный тест, 7 компаний с вакансиями, регулярные задания, историю приглашений.

Полезные команды: `make ps`, `make logs`, `make seed`, `make reset` (пересоздать демо-данные), `make down`.

### Публикация фронтенда отдельно от стека

Фронтенд публикуется на https://fsp.prowebcraft.ru, стек (API, Keycloak, БД) остаётся на своей машине и доступен по внешнему IP через проброс одного порта — `HTTP_PORT` (18088, nginx фронтенда стека).

Адрес бэкенда задаётся явно при старте контейнера фронтенда (`frontend/nginx.conf.template`): nginx проксирует `/api/` на `BACKEND_URL`, а `/auth/` (Keycloak) — на `KEYCLOAK_URL`. Браузер работает только с доменом фронтенда, поэтому нет mixed content (HTTPS-страница → HTTP-бэкенд) и CORS, а камера цифрового проктора получает HTTPS. Админка Keycloak через `/auth/admin/` закрыта.

```
браузер ──HTTPS──▶ fsp.prowebcraft.ru (TLS-прокси → контейнер фронтенда :5100)
                      │  /api/, /auth/
                      ▼
               http://<внешний IP>:18088 (nginx стека) ──▶ backend:8000, keycloak:8080
```

На машине со стеком — в `.env`:

```bash
PUBLIC_URL=https://fsp.prowebcraft.ru
KEYCLOAK_PUBLIC_URL=https://fsp.prowebcraft.ru/auth
```

затем `make up` и `make kc-public` (добавляет домен в redirect URI клиентов Keycloak, если realm уже был импортирован раньше).

Сборка и деплой — `.github/workflows/deploy-frontend.yml`: на PR образ собирается и проходит smoke-тест (`frontend/scripts/smoke.sh`), на `main` публикуется в GHCR и разворачивается по SSH на `127.0.0.1:$WEB_PORT` хостинга; при неудачной проверке возвращается предыдущий контейнер. TLS и домен — на прокси хостинга (`proxy_pass http://127.0.0.1:5100;` с `X-Forwarded-Proto $scheme`).

| Настройка репозитория | Тип | Значение |
|---|---|---|
| `BACKEND_URL` | variable | Внешний адрес стека без пути, например `http://203.0.113.10:18088` |
| `KEYCLOAK_URL` | variable, необязательно | По умолчанию `<BACKEND_URL>/auth` |
| `WEB_PORT` | variable, необязательно | Порт контейнера на хостинге, по умолчанию `5100` |
| `SSH_PORT` | variable, необязательно | По умолчанию `22` |
| `SERVER_HOST`, `SERVER_USER`, `SSH_PRIVATE_KEY`, `SSH_HOST_FINGERPRINT` | secrets | Доступ к хостингу фронтенда по SSH |

Тот же образ можно запустить вручную: `docker run -e BACKEND_URL=http://203.0.113.10:18088 -e KEYCLOAK_URL=http://203.0.113.10:18088/auth -p 5100:80 <образ>`.

## Локальный запуск без Docker

Требования: Python 3.12+ (в Docker — 3.14), [uv](https://docs.astral.sh/uv/), Node.js 22.12+ (в Docker — 24 LTS).

```bash
uv sync --all-packages   # Python-зависимости всех модулей
make dev                 # реестр ФСП :8090, API :8000, фронтенд :5173 в одном терминале; Ctrl+C — остановить всё
```

Откройте http://localhost:5173 (Swagger — http://localhost:8000/api/docs). Можно запускать и по отдельности, каждый в своём терминале: `make dev-registry`, `make dev-backend`, `make dev-frontend`.

В этом режиме используется SQLite и `AUTH_MODE=dev`: страница входа предлагает демо-аккаунты без пароля, Keycloak не нужен. Это **только для локальной отладки**; привязка ФСП ID — демо-кнопкой по номеру.

## Сценарий проверки

1. **Кандидат:** войти `candidate@demo.fsp` → роль «Ищу работу» и согласие на обработку ПДн → опрос (специализация, стек, ожидания, заявленный грейд) → «Тест и грейд» → пройти тест → категория, например «Backend · Middle» (или тест на уровень ниже).
2. **Работодатель:** войти `employer@demo.fsp` → «Подборки» → «Новая подборка» → вставить текст потребности («Вставить пример») → «Показать подборку» → рекомендованные категории и кандидаты с объяснением → фильтр «есть ФСП» → «Сбросить уточнения» → «Пригласить».
3. **Контакт:** войти `maria@demo.fsp` (или кандидатом из шага 1) → «Приглашения» → открыть (статус «просмотрено») → «Принять» → у работодателя в «Приглашениях» появились ФИО и контакты.
4. **Отклик:** кандидат → «Вакансии» → откликнуться → работодатель → «Вакансии» → «Отклики».
5. **Федерация:** войти `federation@demo.fsp` → воронка трудоустройства участников ФСП в сравнении с кандидатами без ФСП.
6. **Механики:** публичные страницы «Тест из описания вакансии» (`/test-demo`; сама генерация — `POST /api/assessment/preview` — доступна только работодателю, так как отдаёт формулировки заданий из банка) и «Как это работает» (`/how-it-works`).


## Структура репозитория

```
ml/                 ML-ядро (пакет fspml): тестирование IRT/CAT и банк заданий, подбор, NLP, валидация, бенчмарк
backend/            API на FastAPI (модульный монолит), миграции Alembic, seed-данные, тесты
frontend/           React + TypeScript: кабинеты кандидата и работодателя
fsp-registry-mock/  имитация реестра ФСП с предложенной схемой данных
keycloak/           realm-ы Keycloak: платформа (fsp-jobs) и имитация ФСП ID (fsp-id)
```

Стек: Python 3.14, FastAPI, SQLAlchemy 2, PostgreSQL 18, Keycloak 26, React 19, TypeScript, Tailwind CSS 4. ML работает локально на CPU: по умолчанию персональные данные кандидатов не передаются во внешние сервисы (152-ФЗ); Yandex AI Studio (контур РФ) — только опционально, как запасной разбор опыта в резюме (`LLM_ENABLED=1`).
