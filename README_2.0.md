# ФСП Job Board — README 2.0: что изменилось к финалу

Этот документ описывает доработки после обратной связи экспертов на этапе отбора в финал. Базовое описание платформы, запуск и демо-аккаунты — в [README.md](README.md); полная документация — [docs/fsp-job-board-docs.pdf](docs/fsp-job-board-docs.pdf).

## Позиция: для кого платформа

Соревнования ФСП — место, где молодые программисты показывают реальный уровень: командная разработка в сжатые сроки, проверенная жюри и записанная в реестр. При этом у большинства участников нет коммерческого стажа, и работодатели часто не рассматривают их резюме. **Платформа должна в первую очередь помогать молодым талантливым участникам ФСП подтвердить грейд и получить предложение о работе.**

Сама механика (тест на заявленный грейд, обратная механика, «ворота» стека) от этого не меняется. Меняется то, сколько весят подтверждённые достижения ФСП, и то, что они могут заменить строку «место работы» в резюме. Работодатель по-прежнему видит, почему кандидат оказался в подборке.

## 1. Подбор: формула v7

Код: [`ml/fspml/matching/scoring.py`](ml/fspml/matching/scoring.py) — `WEIGHTS_V7`, `weights_for`, `FSP_YEARS_MAX`, `experience_fit(..., fsp=)`, `rank(version=7)`. В поставке `FSP_RANKER=v7` ([docker-compose.yml](docker-compose.yml), [.env.example](.env.example)); бэкенд выбирает версию через `formula_version()` ([`backend/app/modules/employers/service.py`](backend/app/modules/employers/service.py)), та же формула считает соответствие в ленте вакансий и откликах ([`vacancies/router.py`](backend/app/modules/vacancies/router.py)) и порядок в банке кандидатов.

### 1.1 Веса: было → стало

| | v5 (было) | v7 (стало) |
|---|---|---|
| Сила профиля: тест / ФСП / задания | 0.60 / 0.25 / 0.15 | **0.45 / 0.40** / 0.15 |
| Выдача: соответствие / сила профиля / условия / свежесть | 0.40 / 0.30 / 0.20 / 0.10 | **0.35 / 0.35** / 0.20 / 0.10 |
| **Доля ФСП в итоговом скоре** | 0.30 × 0.25 = **7.5%** | 0.35 × 0.40 = **14%** |
| Нет коммерческого опыта при требовании «от полугода» | множитель × 0.5 | ФСП засчитывается как опыт: призёр всероссийских ≈ полгода → × 1.0 |
| Основной язык/фреймворк вакансии отсутствует | штраф только через покрытие | «ворота» × 0.25 (v6) |

Ограничения, которые не меняли:
- **тест главный:** вес теста в силе профиля не ниже веса ФСП;
- **ФСП не заменяет стек:** «ворота» основного стека срабатывают раньше, и победитель международных соревнований без Go на Go-вакансию не попадает (тест `test_fsp_does_not_bypass_core_stack_gate`);
- **ФСП закрывает только нехватку стажа:** бонус за опыт сверх требования даёт только реальный опыт; на Senior вклад ФСП в опыт почти нулевой;
- **отсутствие ФСП не штрафуется:** у кандидата без истории ФСП множитель опыта тот же, что в v6.

### 1.2 Как выбраны веса

Сначала зафиксировали правило выбора, потом сделали перебор. Правило: максимальная доля ФСП, при которой NDCG@10 на синтетической валидации падает не больше чем на 0.01 относительно v6, и вес ФСП ≤ веса теста. Сетка: `ps_fsp` 0.25…0.45, `profile` 0.30/0.35, `FSP_YEARS_MAX` 0/1/1.5/2. Выбрано 0.40 / 0.45 / 0.35 / 1.0: −0.006 к v6. Вариант с `FSP_YEARS_MAX` = 1.5 (−0.011) и вариант с ФСП весомее теста отклонены. Таблица перебора — в docs/matching.md §4.5.

Почему синтетика не может «подтвердить» v7: скрытая истина генератора сама понижает кандидатов без стажа — так сегодня рассуждает работодатель. Поэтому на синтетике мы проверяем только, что не теряем качество, а пользу v7 проверяем на независимой слепой разметке.

### 1.3 Проверка на слепой разметке и живых данных

**bench2** — 700 кандидатов с живыми текстами резюме, 30 вакансий; асессор (Claude) не знает, какая система нашла пару. 18 новых пар из топ-10 v5–v7 доразмечены тем же асессором по той же рубрике, топ-10 размечен полностью.

| Формула | nDCG@10, слепой асессор | nDCG@10, скрытая истина |
|---|---|---|
| v5 (было) | 0.789 | 0.729 |
| v6 (+ «ворота» стека) | 0.812 | 0.665 |
| **v7 (поставка)** | **0.817** | 0.668 |

Скрытая истина bench2 не моделирует важность основного языка (ставит «3» Java-тимлиду без Go на вакансию Senior Go), поэтому v6 с ней расходится. Это было разобрано ещё для v5, см. docs/bench.md.

**bench3 — живые вакансии** ([`ml/fspml/bench/live.py`](ml/fspml/bench/live.py), `python -m fspml.bench.live`). Взяли 10 реальных открытых вакансий Junior/Middle с Хабр Карьеры: тексты лежат в [`ml/bench3/vacancies.json`](ml/bench3/vacancies.json), названия компаний убраны, ссылки на источник сохранены. К ним — 20 обезличенных собирательных профилей ([`ml/bench3/candidates.yaml`](ml/bench3/candidates.yaml)). **Реальных людей среди профилей нет:** собирать чужие резюме без согласия мы не стали, это персональные данные. Профили описывают типичные случаи: студент-призёр ФСП без стажа, джун с годом опыта без ФСП, мидл с опытом и т. п. Это иллюстрация, а не статистика. Что показал прогон:
- **Разбор реальных вакансий нашим NLP:** специализация верна в 9 из 10, грейд — в 5 из 10. Пример ошибки: Junior Java с фразой «взаимодействовать со старшими разработчиками» распознан как Senior. В продукте разбор показывается работодателю с объяснением и исправляется вручную, но это честная граница точности, и ей займёмся следующей.
- **Выдача:** на реальной вакансии «Junior Python Developer» студент-призёр всероссийских соревнований без стажа в v5 стоит на 2-м месте после кандидата с 1.2 годами опыта и более высоким тестом, в v7 — на 1-м. В карточке причина: «Достижения ФСП засчитаны как практический опыт (≈ 5 мес.)». На Java-вакансиях победитель всероссийских соревнований без опыта поднимается на 2-е место. Python-разработчики при этом не обходят Java-разработчиков: ворота стека работают. Участники ФСП без стажа появились в выдаче 18 раз и в v7 поднялись относительно v5 в 9 из них.

### Витрина: один кандидат — два порядка

`python -m fspml.validation.showcase` → docs/fsp-showcase.md. На синтетической валидации выбирается вакансия, где участник ФСП с нехваткой стажа в v7 обходит кандидата с более высоким тестом. Для этой пары показано место в v5 и v7, разложение скора (вклад теста, ФСП, соответствия, множитель опыта), карточка, которую видит работодатель, и топ-10 в обоих порядках. Пример из текущего прогона: вакансия Data Science · Junior (опыт от 1 года). Кандидат с ФСП и 0.8 года стажа в v5 на 3-м месте (множитель опыта × 0.90), в v7 — на 1-м (× 1.00). Кандидат с чуть более высоким тестом и 1.5 годами опыта — 2-й в обоих порядках.

**Где ФСП перевешивает тест.** Внутри категории порядок по-прежнему начинается с теста. Достижения ФСП решают, когда результаты теста близки, а у участника соревнований нет коммерческого стажа. Именно на этом молодых и отсеивали.

## 2. Точность грейда

Код: [`ml/fspml/assessment/cat.py`](ml/fspml/assessment/cat.py) — `CatConfig` (`pass_probability_upgrade`, `upgrade_probability`, `fsp_prior_shift`), `with_fsp_prior`; бэкенд — `attempts.fsp_prior` (миграция `0008`), `fsp_prior_for` и `attempt_config` в [`backend/app/modules/assessment/service.py`](backend/app/modules/assessment/service.py).

**Что значит 68%.** Это доля кандидатов, чей итоговый грейд в точности совпал с истинным, из пяти ступеней (Intern…Lead), на синтетической популяции из 1000 человек. В пределах ±1 ступени точность 99.4%. Ошибки в основном лежат у порогов грейда. **Разбор ошибок** показал, что прежняя настройка ошибалась асимметрично: занижение 29.5%, завышение 2.7%. Пороги повышения (0.75 / 0.8) были строже, чем требовал лимит завышения в 5%.

**Что изменили.** Обе настройки выбраны перебором при ограничении «завышение ≤ 5%»:
1. **Пороги повышения.** Предложить тест на грейд выше — при P(θ > следующий порог) ≥ 0.5 (было 0.8), подтвердить повышение — при ≥ 0.65 (было 0.75). Порог первичного подтверждения не меняли (0.6).
2. **ФСП как априорная информация.** Приор θ в адаптивном тесте сдвигается на 0.8 × силу ФСП. Решение по-прежнему принимают ответы: сильный ФСП-приор при провальных ответах даёт «не подтверждено». Без истории ФСП приор прежний.

| Вариант (та же популяция и сиды) | Точно | ±1 | Завышение | Занижение | Точно, с ФСП | Точно, без ФСП | Взв. κ ретеста |
|---|---|---|---|---|---|---|---|
| Прежняя настройка | 67.8% | 99.4% | 2.7% | 29.5% | 67.8% | 67.8% | 0.82 |
| Только новые пороги | 70.7% | 100.0% | 4.2% | 25.1% | 71.1% | 70.5% | 0.83 |
| Только ФСП-приор | 67.7% | 99.9% | 2.2% | 30.1% | 73.5% | 64.8% | 0.85 |
| **Текущая (пороги + ФСП-приор)** | **74.5%** | 99.8% | 3.3% | 22.2% | 77.4% | 73.1% | 0.83 |

Цена изменения: онбординг в среднем длиннее на 4.6 задания (30.9 → 35.5), так как кандидатам чаще предлагается тест на грейд выше. В строке «Только ФСП-приор» точность без ФСП ниже (64.8%) не из-за приора — у таких кандидатов он не меняется. Причина в том, что все варианты используют общий генератор случайных чисел: путь кандидатов с ФСП меняется, и вслед за ним сдвигаются случайные числа следующих кандидатов. Решение принимается по итоговой строке.

**Проверенная и отклонённая идея — приор по заявленному грейду.** Самооценка как стартовая точка давала ещё около +3 п.п. точности, но увеличивала ложные повышения у тех, кто завысил заявку (≈ 10% → 12%), то есть поощряла бы накрутку. ФСП-приор такой лазейки не даёт: достижения приходят из реестра, а не со слов кандидата.

**Что не изменилось по ТЗ.** По результату теста грейд не понижается. Если попытка повышения провалена, подтверждённый грейд остаётся, а смена грейда возможна не чаще раза в 90 дней.

## 3. Замечания по сервису

### Вебхук `invitation.accepted`
**Причина.** Вебхук брал имя, почту и телефон только из полей профиля, которые кандидат заполняет по желанию. У кандидата, зарегистрированного через Keycloak и не заполнившего профиль, работодатель получал «приглашение принято» с пустыми контактами. Так же вели себя карточка кандидата и письмо работодателю.

**Исправление.** Добавлен один хелпер `revealed_contacts` ([`candidates/service.py`](backend/app/modules/candidates/service.py)), которым теперь пользуются вебхук, карточка, приглашение и PDF. Имя и почта берутся из профиля, а если их нет — из учётной записи. Телефон передаётся, если кандидат его указал: придумать его платформа не может.

**Что в событии теперь.** `invitation_id`, `accepted_at`, `title`, `salary`, `vacancy_id`, а также `candidate`: `id`, `name`, `email`, `phone`, `telegram`, `github`, `category`, `specialization`, `grade` и `fsp_id`, если кандидат не скрыл ФСП.

**Подпись.** Заголовок `X-FSP-Signature: sha256=HMAC-SHA256(ключ, тело)`. Ключ компании `webhook_signing_key` работодатель видит в профиле компании (`GET /api/employer/company`). Ключ выводится из секрета платформы `WEBHOOK_SECRET`.

**Что не меняли.** До принятия приглашения персональные данные никуда не уходят. Принятие приглашения и есть согласие кандидата на передачу контактов.

**Проверка.** Тест `test_fsp_kept_after_failed_upgrade_and_webhook_payload`: до принятия вебхук не отправляется, после принятия имя и почта заполнены (почта — из учётной записи), подпись сходится.

### ФСП ID после проваленного теста
**Что нашли.** Проваленная попытка не меняет ни грейд, ни привязку ФСП: профиль, достижения и `fsp_id` остаются. Это проверено тестом — кандидат с ФСП подтверждает Middle, проваливает Senior, после чего проверяются профиль, карточка работодателя и вебхук. Пустым был сам идентификатор. В карточке работодателя бейдж «Личность подтверждена · ФСП ID» выводился без ID, в API карточки не было поля `fsp_id`, а в PDF-профиле — строки с ФСП ID.

**Исправление.** У карточки появилось поле `fsp_id`. Бейдж показывает «ФСП ID FSP-000123», в PDF-профиль добавлена строка «ФСП ID: …», в вебхук — `fsp_id`. Идентификатор открывается только после согласия кандидата (принятое приглашение или отклик): по ФСП ID в реестре находится ФИО, поэтому до согласия работодатель видит только факт привязки и достижения. Если кандидат скрыл ФСП в настройках приватности, ID не показывается нигде.

**Грейд при провале** не понижается — это требование ТЗ: можно пройти тест на уровень ниже, а смена грейда — не чаще раза в 90 дней.

### Живой протокол
В конец протокола живого пилота (последний раздел документации) добавлен раздел «Результаты». Таблица перечисляет, что измерено и где: точность грейда — валидация; качество подборки — слепая разметка bench2; разбор реальных вакансий — bench3. ## 4. Как воспроизвести

```bash
uv run pytest ml/tests -q                    # в т. ч. test_matching_v7.py и ФСП-приор в test_cat.py
cd backend && uv run pytest tests -q
make validate                                 # точность грейда, абляция порогов и ФСП-приора, NDCG v5/v6/v7 → docs/validation.md

```

Слепая разметка bench2: новые пары — `ml/bench2/blind/batches/add7_01.md`, метки — `ml/bench2/blind/out/claude-opus-5-5/add7_01.jsonl`, прогоны v6/v7 — `ml/bench2/data/runs.json`.

## 5. Ограничения и что дальше

- Синтетика остаётся синтетикой. Живой пилот тестирования (15–20 человек, из них 2–3 участника ФСП) описан в протоколе и не проведён. Первое, что сделаем с ФСП, — проверим на живых участниках, насколько ФСП-приор и пороги повышения согласуются с экспертной оценкой грейда.
- Разбор грейда в реальных текстах вакансий (5/10) — следующая доработка NLP: понижать вес слов «старший/ведущий», когда они описывают коллег, а не позицию.
- Вес ФСП в v7 — осознанное продуктовое решение в пользу молодых участников. Его цена на синтетике — −0.006 NDCG к v6, на слепой разметке цены нет (+0.005).
